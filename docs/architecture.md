# 架构：品味、原则、全景与已知违反

这份文档回答三个问题：**遇到没有硬规则的选择时怎么判**（品味）、**哪些是硬规则**（原则）、
**当前实现离规则有多远**（违反清单）。

改动前读第 5 节的检查清单；改动踩到第 4 节的违反项时，看 [重构计划](./refactor-state-and-interfaces.md)
里那一条是否已排期——**不要在违反项上继续加东西**。

---

## 1. 架构品味

原则是可以背的，品味不行。这一节记录的是本项目在**规则没有覆盖到的地方**反复做出的同一类选择。
它比原则更根本：原则是品味的产物。

### 1.1 让错误不可表达，优先于让错误被发现

防线的强度排序，能上一级就不停在下一级：

```
类型层不可表达  >  运行时断言  >  自动化测试  >  代码评审约定  >  文档提醒
```

已落地的例子：`AccountEvent.account` 是必填结构体字段而非 `Option`——"忘了标账户"不可表达；
`SubscribeMarket` 只收 `Supervised<A>` 凭证——"订阅一个没人看着的 actor"不可表达；
过滤器是 `fn` 指针而非闭包——"过滤判据依赖外部可变状态"不可表达。

反面判据：当你发现自己在写"注意不要……"的注释时，先问一句**能不能让它编译不过**。

### 1.2 宁可停机，不可裸奔

风控依据不可信时受控退出，而不是降级继续。持仓对账确认漂移即 `kill`，因为策略的三道闸门
全都基于本地持仓计算——继续跑等于无风控裸奔。

但这条有个必须配套的前提：**误停机比漏报更糟，所以判据必须能区分真故障与正常波动**。
对账不是"连续 N 次不一致就停"，而是"连续 N 次**差值稳定**的不一致才停"——因为在途成交的
差值每轮都变，真漂移的差值恒定。**没有区分力的判据不配拥有停机权。**

### 1.3 未知不得伪装成默认值

`0` / 空 `Vec` / `None` 被当成事实，是本项目历史上最难查的一类缺陷（专门有一份
[false-zero-audit.md](./false-zero-audit.md) 记录排查结果）。

具体形态：交易所没返回持仓 ⇒ 空仓？取决于那是不是**全量快照**。未 seed 的腿 ⇒ 报 0？
不行，那是"未知"。账本查询失败 ⇒ 返回空 vec？不行，下游会读成"全部已平仓"。

判据：写下一个默认值之前，问**这个默认值和真实值撞车时会发生什么**。撞车代价大的，必须
让"取不到"可区分。

### 1.4 可见性优先于自动修复

管线积压不做 conflation 而是告警；对账只检测不修复；REST 读数绝不写回持仓真值。

理由是自动修复会**掩盖上游缺陷**：如果 REST 能覆盖本地持仓，那么"Fill 丢了"这件事永远
不会被发现，只会表现为持仓偶尔跳变。一个会自愈的系统里，缺陷会一直活着。

### 1.5 如实声明残余窗口

做不到的事写下来，不假装做到了。代码里"**如实声明**"这个词是刻意的标记，出现处必有一段
"这个方案盖不住什么"的说明（如 `seed_position` 的双计窗口、停机三段模型盖不住的回灌边）。

反面：写"竞态已消除"而实际只是变窄了，比不写更糟——下一个人会基于这句话省掉防御。

### 1.6 回测与实盘共享同一份实现

参数漂移不靠纪律，靠结构：撮合是同一个 `SimState`，策略步是同一个 `StrategyRunner`。
任何"实盘特有"的逻辑出现时，先问它为什么不能在回测里表达。

这条也解释了为什么拒绝 conflation：`EmaCalculator` 是逐 tick 的，丢中间 tick 会让 EMA 变成
**负载的函数**，同一段行情在忙时和闲时算出不同的值——那正是"回测调好的参数上线即漂移"。

### 1.7 注释解释"为什么不那样做"

代码本身说 what，注释说 why-not。本项目注释密度高于常规，但内容集中在：备选方案为什么被
否决、这个常量为什么是这个值、这条判据不这样写会漏掉什么。

价值在于**防止回退**：没有 why-not 的地方，下一个人会"顺手简化"回到被否决的方案。

### 1.8 删除优于新增

每次重构记录净实体变化。奥卡姆剃刀在这里是硬要求：能用现有机制解决的绝不引入新概念。
上一轮重构删掉 12 个实体、新增 4 个，这个比例是刻意追求的。

## 2. 原则

CLAUDE.md 的七条是通用的，这里只写**本项目特有的、可以直接判对错的**规则。

### P1 单一权威，派生必须注明为什么不能消除

同一事实只有一个权威宿主。派生副本不是绝对禁止（纯函数、无锁、生命周期解耦都是正当理由），
但**每一份派生都必须在代码里写明为什么不能查权威**。

现行记录：持仓真值的权威在 `PositionLedgerActor`；executor 的那份因为"策略是纯函数、决策中途
不能 await"；metrics 的那份因为"需要持仓 × 价格的 join，且 `on_stop` 快照不能依赖并发停机的
actor"。见 [external-data-access.md](./external-data-access.md) §四。

**新增第四份必须先证明它不能用 `GetLivePositions` 替代。**

### P2 能力用类型表达，不用值域表达

"这个交易所没有账户"不能表达成 `fetch_positions()` 返回空 `Vec`，要表达成没有那个 trait 对象。
"这条腿基线未到"不能表达成 `size = 0`，要表达成结果里没有这条腿。

判据：如果调用方需要**另一个 bool 字段**才能解读返回值，说明能力没有被类型表达。

### P3 接口只暴露消费者需要的

给出去的方法数应当接近被用到的方法数。差距一大，就出现两件事：消费者读到不该读的、
新增字段自动扩大所有消费者的可见面。

### P4 分发只在一处

"这条消息是不是我的"这个判断，必须由**路由方**做一次，不能由每个消费者各判各的。
每个消费者自己 `if not mine { return }` 的形态，在新增一类消费者时不会编译失败——
静默双执行或静默不执行。

### P5 IO 不在 handler 里

邮箱是共享资源。任何 handler `await` 在网络/文件上，都会让该 actor 的**全部**其他消息排在
一次超时后面。正确形态是 `spawn` 出去、结果回投为消息。

配套要求：一旦拉取移出 handler，"结果永不回投"就成为可达状态（任务 panic、请求真挂死），
必须有一道**不依赖回投**的守卫。见 `PositionLedgerActor::check_in_flight_staleness`。

### P6 漏改必须编译失败

新增交易所、账户类型、事件 variant 时，所有必须跟着改的地方要么自动正确，要么编译不过。
`ALL_EXCHANGES` 常量存在的唯一理由就是这个（新增所时它编译失败）。

### P7 观测不得成为权威数据源

`MetricsActor` 明确声明"故障不得拖垮交易"，连定时器挂掉都不 kill 自己。所以它不能当权威——
让一个"允许自己坏掉"的组件供给别人依赖的数据，是把边界反过来了。

反向成立：权威组件可以被观测。持仓账本对外供查，正因为它是被 REST 持续校验的那一份，
**外部读到的数字与风控守卫看到的数字是同一个**。

## 3. 当前架构全景

```text
 交易所适配层                引擎核心                          消费者
 ─────────────              ─────────────────                ───────────

 BinanceActor ┐                                          ┌─> ExecutorActor(策略, per 账户)
 OkxActor     ├─> MarketPubSub ──┬─> IncomeProcessor ────┤
 HlActor      │                  │   (按 symbol/账户路由) └─> (回测: BacktestEngine 直驱)
 IbkrActor    ┘                  │
      │                          │
      └─────> AccountPubSub ─────┼─> PositionLedgerActor (持仓真值 + REST 对账 + 对外供查)
                    ▲            │
                    │            └─> MetricsActor (观测，允许自己坏)
                    │
                    │                        ExecutorActor 产出信号
                    │                                │
                    │                                v
                    │                          OutcomePubSub
                    │                                │
                    │            ┌───────────────────┴───────────────────┐
                    │            v                                       v
                    └── OrderGateway(实盘唯一下单出口)          PaperCounterActor(虚拟柜台)
                             （合成失败/撤单回报回灌）              （撮合回报回灌）

 对外（外部进程/observer）
   流面: SubscribeMarket / SubscribeAccount / SubscribeOutcome  + fn 过滤
   快照面: GetAllSymbolMetas / GetLivePositions                  见 external-data-access.md
```

模块职责：

| 模块 | 职责 | 不该做的事 |
|---|---|---|
| `exchange/*` | 协议编解码、连接、签名；把交易所语言翻译成领域事件 | 不做业务判断，不缓存业务状态 |
| `messaging/` | 事件类型、状态投影 | 不含 IO、不含 actor |
| `engine/live/` | actor 编排、订阅装配、投产/撤下、监督与停机 | 不含策略逻辑 |
| `engine/strategy_runner.rs` | 策略步的纯逻辑（更新状态 → 转换订单） | 实盘/回测共用，不许有分支 |
| `strategy/` | 业务决策，纯函数 | 不碰 IO、不碰 actor、不读墙钟 |
| `sim/` | 撮合状态机 | 实盘/回测共用 |
| `observability/` | 指标出口 | 不当权威数据源 |

## 4. 已知违反

按严重程度排。每条注明违反哪条原则、实证、以及在重构计划里的编号。

### ~~V1 `StateManager` / `SymbolState` 是共享大对象~~ —— **已修复（R2）**

原状与理由见下方保留的原文。现状：拆成四个投影 ——
`SymbolMarket` / `SymbolPositions` / `SymbolOrders`（per symbol，由 `SymbolState` 门面组合）
+ `AccountView`（账户级）。跨 symbol 的持仓容器 `PositionBook` 供只要持仓的消费者使用：
持仓账本的可达方法从 **39 个收到 8 个**。

「seed 之后、快照请求时刻之前的 Fill 要丢弃」这条防双计规则提取到
`SymbolPositions::apply_fill`，与 `seeded_at` 同住一处 —— 账本与策略门面共用一份，
不会各自演化出差别（那种差别的表现是"对账偶尔误报漂移"，最难查）。

**持仓折叠仍是三份宿主**（账本 / executor / metrics），数量没变但性质变了：
账本那份现在最瘦最专一，而它正是唯一被 REST 持续校验的那份。
executor 与 metrics 的保留理由见 [external-data-access.md](./external-data-access.md) §四。

<details><summary>原文（保留以便对照判断标准）</summary>


`StateManager` 19 个公开方法 + `SymbolState` 20 个，装着六类互不相干的东西：per-symbol 行情
（bbo / mark / index / funding）、持仓 + seed 标记、挂单 + 终态记忆 + 超时清理、余额、
账户净值与希腊值、市场状态。

三个消费者各只用其中一块：executor 用「行情 + 持仓 + 挂单」，账本用「持仓 + seed 标记」，
metrics 用「持仓 × 价格 + 挂单 + 账户」。**一个类型有三组互不重叠的使用者，那就是三个类型。**

这是"持仓折叠有三份宿主"的根因：因为持仓和价格被焊在同一结构里，`SymbolState::exposure`
必须在结构内部 join，metrics 才没法只查持仓。→ 计划 R2

</details>

### ~~V2 策略拿得到不属于它的东西~~ —— **已修复（R3）**

原状两条，性质不同：

1. **接口过宽**。`fn on_event(&mut self, event: &IncomeEvent, state: &StateManager)`
   交出 39 个方法。往 `StateManager` 加读方法会自动扩大所有策略的可见面，编译器不报警。
2. **越界投递**。所级读数（`Balance` / `AccountInfo` / `Greeks` / `ExchangeStatus` /
   `ExchangeRate`）没有 symbol，分发层一律**广播** —— 策略读得到自己压根没订阅的所的
   净值与希腊值，而杠杆闸门与 delta 对冲就是拿这些算的。

现状：

```rust
fn on_event(&mut self, event: &IncomeEvent, view: StrategyView<'_>) -> Vec<OutcomeEvent>;
```

[`StrategyView`] 4 个方法 + [`SymbolView`] 5 个，共 **9 个**，就是实测的调用面。
`StateManager` 上那九个账户转发方法一并删除，账户读数只剩 `account_view()` 一条路。

越界投递堵在**分发层**：`IncomeEvent::delivery()` 把投递范围分成
`Symbol(所, symbol)` / `Exchange(所)` / `Broadcast` 三档，
[`SubscriptionScope::accepts`] 据此判定，实盘 `IncomeProcessorActor` 与回测循环调的是
同一份实现。范围外的读数根本进不了策略的 `StateManager`。

> **一次走错方向的记录**。第一版把裁剪做在 `StrategyView` 上（查询时按订阅所过滤）。
> 那是错的，两个原因：它成了"什么算范围内"的第三处实现（P1/P4）；而且**它挡不住**——
> 越界的读数照样随 `&IncomeEvent` 推给策略，payload 里就带着净值，
> 只堵查询不堵投递等于没堵，却在文档里写成了"已修复"（正是品味 1.5 说的那种声明）。
> 审查指出后改到分发层，视图里的裁剪整个删掉。

> **三次统计更正**。本节初稿说调用面是 8 个方法，后更正为 11 个（漏了账户级三个：
> 当时只扫了变量名叫 `state` 的调用点，而策略里那三处叫 `state_manager`）。
> R3 动手时逐个方法核实，**实际是 9 个** —— 之前的 8 与 11 都把"调用点数"和"方法数"
> 混着数了。三次统计两次错，说明这类数字必须逐个方法 grep 后再写，不能凭印象。
>
> 另一处更正：初稿还写过"策略能看到其他 symbol 的状态"，那是错的。
> `StrategyRunner` 用策略自己 `public_streams()` 推导的 symbol 集合去建 `StateManager`，
> 它能查到的 symbol 本来就只有自己订的。

### ~~V3 `ExchangeClient` 用返回空值表达"没有能力"~~ —— **已修复（R1）**

原状：8 个方法把公共行情与私有账户混在一个 trait，无凭证的所把"没有账户"表达成
`fetch_positions` 返回 `Ok(vec![])`；"有没有账户"同时存在于返回值语义与
`ExchangeSetup.authed: bool` 两处。

现状：拆成 [`ExchangeClient`]（公共）与 [`AccountClient`]（私有），
`ExchangeSetup.account: Option<Arc<dyn AccountClient>>`，`authed` 字段删除。
装配处只在配了凭证时才装入，因此"持有该对象"即"有账户"，一处表达、编译期可查。

### ~~V4 两个下单出口各自用否定条件过滤同一条总线~~ —— **已修复（R4）**

原状：两个出口各在自己的 handler 里写否定条件（`!= Live` / `!is_paper()`）。
`AccountId` 只有两个 variant 时互补成立，但新增第三类账户时两处都不会编译失败，
结果要么静默双执行、要么静默不执行。

现状：判据收敛为 `outlet_for` 的穷举 `match`（新增 variant 即编译失败），
订阅过滤器 `to_live_outlet` / `to_paper_outlet` 在装配处紧挨着写，
`outlet_dispatch_tests` 用这两个函数本身断言"每条信号恰有一个出口接受"。
两个出口保留一句基于同一判据的**到站断言**（装配写错时响亮失败，而非静默双执行）——
投递路径在类型上收不死，这是品味 1.1 阶梯的第二级。

### V5 停机三段模型盖不住回灌边 —— 已知并接受

`producers → buses → consumers`，但 Outcome 的两个消费者会倒回来往 Account 总线发。
代价是停机瞬间丢最后一批回报（最终一次指标快照少记一笔）。已在 `manager/mod.rs:107-119`
论证过救不回来（柜台的延迟管道是 spawn 的，`on_stop` 不排空它）。

**不修**。列在这里是为了提醒：新增消费者时先问它会不会回灌。

### V6 manager 承担四件事，1951 行 —— 违反 P3（弱）

装配 / 投产撤下编排 / 监督树根 / 停机链根 / 总线持有 / 快照面应答。
`provisioning.rs` 那 1039 行的投产编排是独立领域流程，与监督/停机没有内在联系，
只是恰好都需要子 actor 句柄。不阻碍扩展，但它是全系统最难改的一处。→ 计划 R5

### V7 观测口径泄漏进领域状态 —— 违反 P3

`SymbolExposure::session_notional_delta`（把重启前存货从盈亏里剔除）是 metrics 的概念，
却住在三方共用的 `SymbolState` 上。生产代码里 `exposure()` 只有 `metrics.rs:160` 一个调用点。
→ 计划 R5

## 5. 改动前的检查清单

1. 这个改动落在全景图的哪一层？是否与该层的"不该做的事"冲突？
2. 我在新增实体吗？现有机制为什么解决不了？（品味 1.8）
3. 我写的默认值，和真实值撞车会发生什么？（品味 1.3）
4. 我在写"注意不要……"的注释吗？能不能让它编译不过？（品味 1.1）
5. 我新增了一个消费者吗？它自己判断"这条是不是我的"了吗？（P4）
6. 我在 handler 里 `await` IO 吗？（P5）
7. 我新增了一份状态副本吗？为什么不能查权威？写下来了吗？（P1）
8. 新增交易所/账户类型/事件 variant 时，漏改的地方会编译失败吗？（P6）
9. 我声称消除了某个竞态——它真的消除了，还是只是变窄了？（品味 1.5）
10. 这个改动踩到第 4 节的违反项了吗？**不要在违反项上继续加东西。**
