# 引擎对外开放数据的统一机制

外部代码（观测导出、通知、复盘账本、运维脚本）需要引擎里的数据。本文定义**两个面**及各自契约：
数据按性质选面，不为单个消费者开特例。

```text
                      ┌────────────────────────────────────────┐
   流（推）            │  market_bus() / account_bus()          │
   连续、增量、有序     │  outcome_bus()  + inbox.subscribe      │
                      └────────────────────────────────────────┘
                      ┌────────────────────────────────────────┐
   快照（拉）          │  all_symbol_metas() / symbol_meta()    │
   启动后不变的目录     │                                        │
                      └────────────────────────────────────────┘
```

两个面都经 `ManagerHandle`（`run_engine` 交给装配闭包的句柄）。

## 一、流面：三条总线

三条总线覆盖引擎里全部事件类型，订阅时按 `fn` 指针过滤：

| 总线 | 覆盖 |
|---|---|
| `market_bus()` | `MarketData` 全部 variant：BBO、MarketTrade、MarkPrice、IndexPrice、FundingRate、Candle、HistoryCandles、ExchangeStatus、Clock、Custom |
| `account_bus()` | `AccountData` 全部 variant：OrderUpdate、OrderRequest、Fill、Balance、FundingFee、Greeks、Equity、PositionValues（持仓账本发的持仓读数，见 §三） |
| `outcome_bus()` | 策略信号（下单 / 撤单 / 自定义事件），带 `account` 标签 |

**契约**

- 订阅只能经收件箱（`Inbox::subscribe`），收件箱只能从任务树上的 `Scope` 建 —— 观察者经
  `ManagerHandle::observers()` 挂到 manager 的消费者组，在自己的构造闭包里订阅。"订一个没人看着的组件"
  不可表达：观测组件悄悄死掉而引擎照常交易，是最危险的一类故障（挂在树上的观察者出错即整机停机）。
- 过滤器是 `fn` 指针而非闭包：不许捕获状态，因此筛选判据是纯粹的事件形状判断，可被独立推理。
- **必须带 `account` 判据**：实盘与模拟账户共用 `AccountBus`，靠事件自带的 `account` 区分。不筛的话
  模拟成交会混进实盘口径。
- 投递进订阅者的无界收件箱：消费者跟不上时后果是积压（可见，见 `Executor::check_pipeline_lag`），不是丢事件。

**新增一个事件类型时，流面不需要任何改动** —— 订阅方的 filter 自动可见新 variant，manager 一行不用改。

## 二、快照面

有些数据不是流。目前只有合约目录（`ManagerHandle` 的同步方法）：

| 方法 | 应答 | 语义 |
|---|---|---|
| `all_symbol_metas()` / `symbol_meta(ex, &sym)` | 各所交易规则 | 精度、步长、合约乘数；读句柄里那份启动时预加载、此后不变的目录 |

**契约**（新增一项快照必须都满足，否则不该进这个面）

1. **纯内存读**。应答路径上不许有任何 IO —— 不打 REST、不读文件、不推送。
2. **不阻塞收件箱**。数据宿主处理任何消息时都不得 `await` 在 IO 上，否则查询会排在一次网络超时后面。
3. **只经 `ManagerHandle` 暴露**，外部只持有这个句柄，内部组件的地址不外泄。
4. **不许合并成一条通用查询**。新增一类快照 = 新增一个句柄方法，不改既有分支。

## 三、持仓：只从持仓账本的读数拿

持仓是对 Fill 流的折叠，折叠需要初值（启动时交易所侧的存量），而且**刻意不周期性重发**：
持仓真值由「投产期 REST 基线 + 之后全程 Fill 累加」维护，REST 只用于对账，不许覆盖权威状态。
所以外部不能自己从 Fill 流折一份 —— 那份没有对账保护，漂了没人知道。

持仓的出口是持仓账本（`PositionLedger`）发到账户总线上的 **`PositionValues`**：每笔实盘成交后发
该所一份、每个对账节拍（3 秒）发全部所一份，每个已跟踪币一条：持仓数量（带符号，币本位）+ 估值价
（盘口中间价）。账本里有仓的币还没有盘口时整份不发（价值未知，不当 0）；只含基线已写入的腿
（未写入 = 未知，不出现，不能当 0）。

**消费者一律读它**（#812）：

- 策略的账户杠杆闸门（`StrategyView::position_values`）；
- 指标（看板上的持仓、各所持仓价值、会话盈亏，都按所按币种），见 `engine/live/metrics.rs`；杠杆是策略的口径，由策略读同一份读数自己推。

于是看板上的杠杆与风控闸门看到的是**同一个数**（账本读数之和 ÷ 交易所报的净值），不会出现
「看板绿着、引擎却在停机边缘」。外部观察者要持仓也订这条：`account_bus()` 过滤
`ExchangeAccountData::PositionValues`，按 `account == Live` 取实盘。

## 四、持仓折叠的两份宿主：一份权威，一份有理由的本地派生

| 宿主 | 角色 | 为什么不能消除 |
|---|---|---|
| `PositionLedger.reconciler.mirror` | **权威 + 对外** | 唯一被 REST 持续校验的那份，因此唯一有资格叫真值 |
| `Executor` 的 `StrategyRunner.state` | 决策用 | 策略是**纯函数**，决策中途不能 `await`；且要在自己的成交到达的同一拍里看到它 |

两份都是同一条 Fill 流、同一份 seed 语义、同一条防双计规则的确定性结果。「除非有 bug 不会分叉」
不靠信：账本每个节拍向每个实盘 executor 要一份已 seed 的持仓（`ExecutorHandle::seeded_positions`），
按同一判据比对（差值稳定连续 N 次即致命，#694），于是 executor ≈ 账本 ≈ 交易所两条比对串起来。

**新增第三份必须先证明它不能用 `PositionValues` 读数替代。**（#812 前指标自己折了一份并用自己的
盘口估值、看板杠杆又用交易所报的持仓总值，三个数各不相同，已删。）
